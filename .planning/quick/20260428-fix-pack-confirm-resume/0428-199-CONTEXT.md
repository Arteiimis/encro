# Quick Task 0428-199: 修复恢复进度时打包流程跳过用户确认的问题 - Context

**Gathered:** 2026-04-28
**Status:** Ready for planning

<domain>
## Task Boundary

修复视频处理路径在恢复已有进度时的打包确认问题。当webp编码流程已经结束、只剩打包流程未完成时，系统应立即开始打包而不提示用户确认。同时验证图片处理路径是否有相同问题。

代码探索发现：
- **视频路径** (`video_process.cpp:303`): 编码后自动调用 `maybePackWorkflowOutputs()` 打包，**无用户确认**
- **图片路径** (`picture_process.cpp:290`): 已有 `confirmPicturePack()` 函数，**正确询问用户**
- **根本原因**: `shouldEnableJobState()` 对视频默认启用 job state（`pipeline.cpp:20-24`），导致恢复时编码完成后直接进入打包阶段

修复范围：
- 仅修复视频处理路径
- 仅在恢复场景下添加确认（fresh run 保持自动打包行为不变）
- 图片路径无需修改（已有 confirmPicturePack）

</domain>

<decisions>
## Implementation Decisions

### Confirmation Placement
- **仅在 resume 场景下提示**：正常 fresh run 保持当前自动打包行为不变
- 检测条件：job state 存在 + 所有编码任务已完成 + 打包任务未完成
- 不影响 fresh run 的正常流程

### Resume Prompt Wording
- 在 resume 且所有编码已完成时显示：
  `"All encodes already complete. Do you want to proceed with packing? (y/N): "`
- 使用 `readUserIpt(ctx.config.yesToAll, ...)` 保持一致风格

### --yes/-y Flag Behavior
- `--yes`/`-y` skip both encode and pack confirmations — 与现有 `yesToAll` 语义一致

### Picture Path
- 无需修改 — `picture_process.cpp` 已有 `confirmPicturePack()` 且默认不启用 job state

</decisions>

<specifics>
## Specific Ideas

### 修改位置
在 `video_process.cpp` 的 `runScannedEncodingWorkflow()` 中，在编码完成后、调用 `maybePackWorkflowOutputs()` 之前：
- 检查是否存在 job state
- 检查是否所有编码任务都已完成（恢复场景）
- 如果是恢复且所有编码已完成，显示 pack 确认提示
- 用户拒绝则跳过打包直接返回

### 参考模式
- 图片路径的 `confirmPicturePack()` (`picture_process.cpp:290-295`) — 确认函数模板
- `runEncodingTasks()` 中的编码确认 (`video_batch_execution.cpp:710-721`) — `readUserIpt()` 用法

</specifics>
