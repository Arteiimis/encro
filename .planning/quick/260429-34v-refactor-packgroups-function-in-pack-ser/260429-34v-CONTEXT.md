<domain>
## Task Boundary

Refactor the `packGroups` function in `src/pack/pack_service.cpp` (currently ~184 lines, lines 198-381). The function is too long with excessive inline nesting — particularly the task lambda (~80 lines) and interleaved compact/full-progress logic. Goal: reduce length through extraction while preserving all existing behavior and test expectations.

</domain>

<decisions>
## Implementation Decisions

### Extraction granularity
- **Medium (4-5 helpers).** Extract: (1) compact progress bar initialization, (2) spinner thread lifecycle, (3) task builder with compact per-file callback, (4) spinner cleanup + final "Packed" status. Main `packGroupsCompact()` becomes a clean ~40-line orchestrator.

### Progress state encapsulation
- **Local struct.** Define a `CompactProgressState` struct (anonymous namespace in `pack_service.cpp`) bundling: `progress::ProgressContext`, `std::optional<std::size_t> barIndex`, `std::size_t completedFileCount`, `std::atomic<std::size_t> completedArchiveCount`, `std::mutex mutex`, `std::atomic<std::size_t> finalizingCount`, `std::atomic<bool> spinnerStop`, `std::jthread spinnerThread`. Extracted helpers take a `CompactProgressState&` reference. Minimizes parameter passing.

### Compact vs non-compact separation
- **Separate fully.** Split into `packGroupsCompact()` and `packGroupsFull()` entry points. `packGroups()` dispatches to the appropriate one based on `plan.compact`. Each function is self-contained and simpler — no `if (plan.compact)` conditionals needed in either.

</decisions>

<specifics>
## Specific Ideas

- The file callback lambda (lines 268-303) and archive completion hook (lines 320-341) share identical compact-bar-setter logic — both check `finalizingCount == 0`, then set postfix and call `onCompactStatusText`. These should be unified into a single helper method on `CompactProgressState`.
- The non-compact path (`packGroupsFull()`) is straightforward — the existing logic minus compact conditionals. The task lambda uses `taskCtx.progress` directly.
- No changes to test expectations — the same status text formats and callback sequences must be preserved.

</specifics>
